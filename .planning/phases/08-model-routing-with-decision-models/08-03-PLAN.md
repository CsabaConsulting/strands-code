Planner resolutions. Executor implements exactly these; no re-derivation.

1. Setup flow order under /route setup: scope radio (global versus repo) then engine radio (openrouter versus local) then candidate picks then decision-model pick then local-model text when engine is local then directive lines then write plus summary. Every radio uses radio_choice with a typed input fallback off-tty; ESC or empty input aborts with the session unchanged (D-13).
2. Candidate picks: repeated radio over the chat-capable catalog sorted by price ascending with a Done entry, at least one required; off-tty accepts a comma-separated id list validated against the fetched catalog with unknown ids rejected and re-prompted once. Decision-model pick: single radio over catalog entries advertising response_format or structured_outputs support, price ascending, explicit choice required with no default. Directives: repeated input lines until a blank line, joined as the directives string; empty directives allowed with a confirm. No hardcoded model names anywhere in setup (D-13, D-06).
3. save_strategy writes the resolved schema via yaml.safe_dump through tmp-write plus os.replace with the parent dir at 0700; refuses symlinked targets with ValueError; rejects api_key-shaped keys by warning and dropping them; refuses to write zero usable candidates. Repo scope writes the repo path, global scope the global path (D-13, D-03).
4. validate_strategy returns a report listing the winning source file, one line per candidate (ok or the skip reason), engine checks (decision model known in the cached catalog when reachable else unchecked, local model configured when primary is local), and the directives presence note; /route validate prints the report as a reply and names manual-edit fixes per failure class (D-13).
5. docs/ROUTING.md holds the routing guide: concepts, the two example strategies (cheap-default single tier plus tiered team file), manual-edit rules, the repo-wins note, the never-keys note, and the stay-on-current tie-break note. Examples carry a pulled date and a re-validate pointer, never live catalog claims (D-13).
6. Single-candidate fast path: decide with exactly one usable candidate advertising at least one level returns a pick-shaped verdict (model the candidate, effort its first advertised level, why `only candidate`, engine `none`) with zero engine calls, so the unchanged hook takes its pick branch and prints the standard Routed line; spend and events record zero decision tokens. A single candidate with no advertised levels falls through to the normal engine chain. Multi-candidate behavior is unchanged (D-08).
7. Live integration tests: OpenRouter decision tests run only with OPENROUTER_API_KEY set using a cheap catalog id resolved at test time, marked integration; Ollama tests run against a stdlib stub HTTP server in-test by default and against a real daemon only with OLLAMA_LIVE set. No live test may fail for missing keys or a down daemon: absence skips with the reason (D-06).
8. Excluded here by locked decision, not deferred silently: benchmark live-pull mechanics (A-07 unverified stretch; snapshots stay user-editable per D-02) and fully automatic routing with no override (locked out).

Open Question dispositions (RESOLVED): OQ4 RESOLVED by item 8 jointly with 08-01 item 12 (no live benchmark pull; snapshots stay user-editable); OQ5 RESOLVED by item 2 (explicit decision-model choice required, no default).
