### 1.2 String grammar (deterministic — `interventions.py:1-60`)

`_resolve_one(value, ask)`:

- `"off"` → `None` (no handler).
- `"ask"` → `HumanInTheLoop(ask=ask)` — every non-allowed tool requires approval.
- `"smart"` → `HumanInTheLoop(classifier=True, ask=ask)` — built-in LLM risk classifier flags risky calls only.
- string ending `.cedar` → `CedarAuthorization(policies=...)` (needs `strands-agents[cedar]` extra; **not installed** — rule out Cedar for this phase).
- **any other string** → `HumanInTheLoop(classifier=LLMClassifierConfig(system_prompt=value), ask=ask)` — natural-language policy becomes the classifier prompt.
- inline Cedar text is intentionally NOT auto-detected; non-`.cedar` strings always mean NL policy.
- a raw handler instance passes through untouched (custom `ask`, trust rules reachable).
- `resolve_interventions(value, *, ask=None)` coerces to `list[InterventionHandler]`; `agent.py:548` passes the result as SDK `interventions=`.
- **Collision rule** (`_check_handler_collisions`): at most one handler per `name`; two `HumanInTheLoop` instances collide (`name = "strands:human-in-the-loop"`, `hitl.py`). Layering a Cedar policy + one human gate is allowed; two human gates are not. Consequence: the TOOL-03 design gets **exactly one** `HumanInTheLoop` instance — policy pre-check + allowlist + ask customisation must all live inside that one instance (custom `ask` callable and/or custom classifier object, not two handlers).

### 1.3 `create_harness(interventions=...)` semantics (`agent.py:388-394`, `459`, `548`)

- Default `None` = off, every call runs.
- Accepts preset (`"ask"`/`"smart"`), NL policy string, `.cedar` path, handler instance, or a list layering Cedar + one human gate.
- **Planner decision, not free:** D-05 mandates deterministic TOML allow/deny, and the discussion log explicitly rejected NL classification as nondeterministic. Therefore `"smart"` and NL-policy strings are **ruled out** as the decision mechanism. The correct shape is `interventions=[HumanInTheLoop(allowed_tools=[...], ask=<custom policy ask>)]` constructed in app code and passed as an instance — sugar strings cannot express TOML deny-wins matching. `allowed_tools` alone is only a name allowlist (no path/command matching), so it covers D-09 reads (`["read"]` plus local `search`, which is not a harness builtin) but the path/command logic must live in the custom `ask`/classifier.

### 1.4 `HumanInTheLoop` ask callable contract (`strands/vended_interventions/hitl/hitl.py:27-190`, `232-259`)

- Signature: `__call__(self, prompt: str, **kwargs: Any) -> Any | Awaitable[Any]` — may be sync or async (async lets the event loop keep serving while waiting).
- `ask="stdio"` builds a stdin prompt (`_create_stdio_ask`, lines 53-84): `(y/n)` or `(y/n/t)` suffix, `threading.Lock`-serialised, `input()` offloaded via `asyncio.to_thread`. Not cancellable mid-prompt — interactive CLI only. The repo should **not** use `"stdio"` directly because D-01 requires full-detail prompts (exact command/diff + risk reason) and D-03/D-04 require remember/batch behaviour; a custom `ask` that renders via `output_context` is needed.
- Custom `ask` return semantics (lines 232-251): return a concrete response; returning `None` is treated as **fail-closed deny** (`Deny(reason=...)`), never passed to `Confirm`; if the callback raises, the exception propagates and aborts the run (fail-closed) — the callback must catch internally and return a deny value if it prefers skip-and-continue.
- Approval test is `default_evaluate` (`strands/interventions/actions.py:26-40`): accepts `True`, `"y"`/`"yes"` case-insensitive. A custom `evaluate=` can accept richer answers (e.g. `"always"` → approve + append policy rule for D-03), but note the D-03 "always deny" write must happen in the `ask` layer (which sees the rule dimensions), not in `evaluate` (which sees only the response value).
- Prompt construction today (line ~216): `f'Approve "{tool_name}"{reason}?\n  Input: {input_json}'`. A custom `ask(prompt, **kwargs)` receives this string; for D-01 the planner should either (a) pre-format a full-detail prompt and ignore the handler-built one, or (b) keep tool/input JSON and prepend the diff/command + risk line. The `BeforeToolCallEvent` (with `event.tool_use["name"]`, `event.tool_use["input"]`) is visible to a custom **classifier** but NOT to `ask` — so any per-action policy matching on path/command must happen either in a custom classifier (`HumanInTheLoopClassifier` protocol, `classifier.py:19-33`, returns `ClassifierResult(requires_human_in_the_loop, reason)`) or by closing over the known action inside `ask` via the prompt string. Recommended: **custom classifier object for TOML matching** (has the event with tool name + input) + **custom `ask` for rendering** (full detail, batch, remember). Both attach to the single allowed `HumanInTheLoop` instance.
- `allowed_tools` semantics (lines 135-145): tools listed run freely; `"*"` allows all; `"!tool"` forces approval and cannot be trusted. Precedence in `_requires_approval` (lines 253-276): `!tool` → runtime-trusted → `"*"` → listed → classifier → default-require-approval.
- `enable_trust=True` remembers approvals in `agent.state[_TRUSTED_TOOLS_KEY]` (`hitl.py:30`) for the session — a per-tool granularity that is **coarser** than D-03's per-rule "always deny this" and D-04's per-turn batch. Do not confuse the two: D-03/D-04 need TOML-file rules and prompt-level batching, not `enable_trust`. D-12's "trust parent approval" policy option could map onto this mechanism or onto subagent construction (see §1.5), planner's call.

D-12 (inherit-and-prompt default) rides on this with no extra code.

The D-12 "trust parent approval" policy option therefore cannot be implemented by widening the child — it must be a policy-level flag the gate reads (e.g. skip prompting in delegated turns when set), or a separate child config. Note `MemoryManager` instances are explicitly NOT forwarded (`agent.py:376`); interventions ARE — confirmed for D-12.
- Noise warning carries over from 02-RESEARCH §6.5: inherited prompting inside delegated turns is noisy; D-04 batching should apply per-turn including delegate turns.

## 3. TOML policy design inputs

- **Stdlib available, no new dependency.** `tomllib` imports cleanly on the repo's Python 3.14.7 (verified this session). `tomllib` is read-only — D-03's "append a standing rule" write-back needs either a TOML writer (new dependency — avoid) or a minimal append/serialise of the repo's own rule schema (recommend the latter: rules are simple allow/deny lists the repo can re-emit without a general writer). Planner to decide; flag any new dependency against the "no new dependency" Phase 2 precedent.
- **Precedent shape:** `DiffConfig` (`diff_config.py:37-94`) — dataclass, `load(path=None)` fail-soft, `save(path=None)` atomic, `platformdirs.user_config_dir("strands-code")` home, never repo-relative. The policy store mirrors this with two lookup roots (D-08): repo `./.agent/policy.toml` overrides home default (`~/.config` home file — concretely the platformdirs user-config dir, same as `default_diff_config_path`). Lookup order (repo wins) is flagged **costly reversibility** in CONTEXT D-08 — planner must spec merge vs override precisely (discussion says "overrides"; decide whether repo *replaces* home or *layers* over it — "layering" with deny-wins across both files is the safer reading, but it must be stated).
- **Rule-match dimensions (D-06):** tool name + path globs (file tools) or command prefixes (shell). Inputs available at the decision point: `BeforeToolCallEvent.tool_use["name"]` + `tool_use["input"]` (input JSON shapes: file tools take `path`; `shell_tool(command, timeout=...)`). Glob matching: stdlib `fnmatch`/`pathlib.PurePath.match` suffices (no new dep); command matching: prefix list per D-06 ("safe subcommands can be pre-allowed") — normalise leading whitespace, decide `sh -c` wrapper handling explicitly (see §6.4).
- **Deny-wins evaluation (D-07):** on conflict (allow+deny both match) deny wins. Evaluation order: collect all matching rules across both files → if any deny matches → deny (prompt? or hard-deny — planner must state whether a deny rule prompts or silently refuses; D-02's skip-and-continue suggests hard-deny-with-explanation is acceptable, but D-01's transparency suggests showing the matched rule); elif any allow matches → proceed without prompting; else → prompt (deny-first default, D-09: reads/search pre-allowed via default allow rules, mutations prompt).
- **Defaults (D-09):** fresh install pre-allows `read` + `search`; `write`/`edit`/`shell`/`python_repl` prompt until policy says otherwise. Implement as built-in default rules (shipped in code), not as a generated file — avoids first-run file creation and matches `DEFAULT_MODE` precedent (`diff_config.py:27`).
- **Scope expansion as rules (D-13):** paths outside cwd+`/tmp` denied unless an allow rule names them. Mechanically: the policy decision runs **before/around** `scope.confine` — an allow rule for an outside path must widen the effective roots for that action, otherwise `confine` raises before the policy is consulted. Planner must order these two checks (recommend: resolve → policy match (may grant extra roots) → confine against union → prompt unless allowed).
- **Schema is the agent's discretion** (CONTEXT): key names, rule fields, glob-vs-regex syntax are the planner's call. Recommended starting shape (planner to finalise): `[[allow]]` / `[[deny]]` lists with `{tool, path|command}` keys — but this is a user-facing contract with **costly reversibility** (D-05), so the plan must print the full schema.

## 5. Coordinating gate approval with `/diff` modes (D-10: no double-prompt)

- **Current `/diff` modes** (`diff_config.py:26-27`): `approve-each` (per-hunk `ask` inside the turn, `diff_gate.py:251-257`), `on-demand` (stash to `PendingStore`, review via `/diff apply`, `router.py:90-94`), `auto` (apply directly). Default `on-demand`.
- **The double-prompt hazard:** with both the Phase 2 diff-gate `ask` and the Phase 3 intervention `ask` active on `write`/`edit`, one mutation would prompt twice (once per layer).
- **D-10 rule:** one prompt total covers the write; `/diff` review remains available on demand but never re-asks for the same change.
- **Coordination options for the planner (pick one):**
  1. *Gate subsumes approve-each:* when the interventions gate is active, the diff-gate wrappers delegate their approve-each decision to the gate's verdict (pass-through), keeping only their diff rendering + stash/apply machinery. On-demand/auto modes are then orthogonal (stash vs apply is not approval — no double prompt by construction).
  2. *Gate skips what the diff-gate approved:* the policy classifier treats write/edit calls already approved in-turn as proceeded. Requires threading the verdict between layers — more coupling.
  3. *Retire diff-gate prompting:* `approve-each` mode is removed/aliased once the gate lands; `/diff` becomes review-only (show/apply/discard). Simplest, but changes a Phase 2 user-facing mode — check Phase 2 lock status before choosing.
- **Invariants regardless of option:** `/diff apply` of stashed changes must not re-prompt (the stash was already gated at stash time, or the apply is a router-side filesystem write outside the agent turn — `apply_stashed` uses `_fs_write`, not a tool call, so the intervention never sees it; state this explicitly); `auto` diff mode + gate approval composes as gate-prompts-once-then-applies; batch prompts (D-04) list each action once.
- **Test pointer:** existing gate tests (`tests/test_diff_gate.py`, `tests/test_tool_surface.py` per 02-SECURITY) pin the diff-gate contract; add a no-double-prompt test (one write under approve-each + gate active → exactly one `ask` invocation).

## 6. Risks for TOOL-03

1. **Two `HumanInTheLoop` instances collide (BLOCKING).** The SDK registers at most one handler per `name` (`hitl.py` note; harness `_check_handler_collisions` raises). The plan must construct exactly one `HumanInTheLoop` carrying allowlist + classifier + ask. Any design with a separate "policy handler" and "prompt handler" fails at construction.
2. **Shell timeout still unpinned (residual from 02-SECURITY #2).** `ShellConfig` exposes only `description` (`types/agent.py:73-80`); the 120 s SDK default (`shell.py:54-64`) cannot be set from repo code. Either confirm/pin in Phase 3 or re-record as accepted upstream behaviour. Long-running `curl`/uploads make this livelier than in Phase 2.
3. **Deny mechanics unverified (D-02).** `Deny` "cancels" the call with the reason shown to the model (`actions.py:57+`); whether the turn then continues gracefully (agent explains what it didn't do) vs stalls/loops is assumed, not evidenced in this repo. Plan a live-turn verification: deny a write and observe the agent's next move. If the agent retries identically in a loop, a `Guide` action or prompt steering is needed.
4. **`sh -c` / pipe / redirect evasion of command-prefix rules.** `shell("sh -c 'curl ...'")`, pipes (`curl x | sh`), `VAR=curl; $VAR ...`, and `echo > file` redirection all defeat naive prefix matching. D-06/D-14 accept prefix matching; the plan must state the normalisation level (strip `sh -c`? scan full command string for pattern substrings vs strict prefix?) and document the residual. Recommend substring-scan for network binaries + prefix-match for pre-allowed safe subcommands, with the exotic-binary bypass already accepted in D-14.
5. **`python_repl` granularity (D-11).** The intervention sees the tool call (`python_repl` + code string) but cannot confine `open()`/`socket` inside the executed code. Gating shows the code (good) but approval is all-or-nothing per execution. The smolagents allowlist precedent (`local_sandboxed.py:13-34`) is defence-in-depth, not enforcement. State that `python_repl` approval does not imply file/network confinement inside the snippet.
6. **Scope-check vs policy-check ordering (D-13).** If `confine` runs first, an allow rule for an outside path can never fire (the `ValueError` precedes the match). If policy runs first, a buggy rule could widen scope silently. Plan the order + tests (outside path with allow rule → allowed; without → denied naming roots, preserving `test_tool_surface.py:91`).
7. **Policy-file write safety (D-03/D-08).** The gate appends rules to `./.agent/policy.toml` (repo-local) — a self-modifying policy the agent triggers. Risks: agent-injected over-broad rules (`tool="*"` allow), TOML corruption (no stdlib writer — hand-rolled serialiser must round-trip), symlink attacks on the policy path (mirror `DiffConfig`'s symlink refusal). Recommend: append-only narrow rules derived from the denied action (never `*`), atomic tmp+replace write, symlink refusal, and a `/policy show`-style read path for user review.
8. **Batching vs exactness (D-04).** Repeated similar actions collapse into one prompt — but the HITL handler fires per tool call (`before_tool_call` per event). Batching therefore cannot live inside the per-call handler alone; it needs a turn-level collector (debounce/collapse window) or a pre-scan. The plan must say where the batcher lives; a naive per-call prompt violates D-04 under multi-file edits.
9. **`programmatic_tool_caller` as a bypass.** It runs Python that can call the agent's other tools (harness docstring, `agent.py:314+`). If enabled by default and unlisted, it inherits gating per inner call only if the sandbox routes inner calls through interventions — unverified. Planner to check whether this builtin is live and whether inner calls are gated; if not, pin it off or gate it explicitly.
10. **Phase 4 vocabulary collision.** `DiffConfig` docstring already warns (`diff_config.py:4-7`): diff modes (`approve-each`/`on-demand`/`auto`) must not clash with Phase 4's Plan/Act mode system. The policy file adds a second persisted-mode vocabulary — keep the names distinct (`policy.toml` allow/deny vs diff modes vs Plan/Act).
11. **Policy-load failure posture.** `DiffConfig.load` is fail-soft on corrupt files but fail-loud on symlinks/unknown keys. For a security gate, fail-soft on a corrupt policy means "prompt on everything" (safe default) — verify the plan states this direction explicitly; fail-open (allow-all on corrupt file) would invert deny-first.
