Planner resolutions. Executor implements exactly these; no re-derivation.

1. Queue visibility (Discretion): on submit while a side answer runs, echo "> /btw <question>" plus "Side question queued (#<depth> in line) — answering in parallel."; on submit while idle-side, echo "> /btw <question>" plus "Side question noted — answering in parallel."
2. Queue is unbounded FIFO (RESEARCH Open Q3 recommendation): no silent loss per D-10; depth echo is the attention control. No cap, no eviction.
3. D-11 primary is prompt_async multiplex: drive the idle prompt with PromptSession.prompt_async multiplexed against broker.poll in an asyncio wait FIRST_COMPLETED loop; a broker request suspends the async prompt, runs the tagged dialog, then re-issues the prompt; a completed line returns to run_loop; btw completion delivers fenced under output_context on the pump thread.
4. D-11 fallback if the spike fails: bounded-wait — btw approvals while main-idle wait for the next main turn, announced once in the transcript as "btw approval needed — will prompt when the next turn starts." D-11's letter still holds for the non-approval path. The spike is timeboxed to one focused session, not days.
5. Drain order: on btw completion the pump starts the next queued question before checking main completion; boundary flush still appends every completed Q&A at the main-turn end.
6. New main turns attach: when run_loop starts a turn while btw runs, the turn re-enters the dual pump with the live btw future attached (no rebuild, no restart of the side run).
</resolved_open_items>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| queued-input→pump | Queued questions are user text held in memory; spawned in order on the main thread, never from the reader |
| idle-terminal→delivery | Idle delivery and dialogs share one terminal owner (the pump thread) under a single output context |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
